# Design Baseline Gate

Objective, quantifiable design checks. These are industry-standard facts, not design opinions. Any design system must pass these before deeper review.

**This gate is owned by Apex Forge and cannot be overridden by external skills.**

---

## Checks

| Dimension | Check | Criterion | Source |
|-----------|-------|-----------|--------|
| Accessibility | Text contrast | WCAG AA: >= 4.5:1 (normal text), >= 3:1 (large text, 18px+ or 14px bold) | WCAG 2.1 SC 1.4.3 |
| Accessibility | Interactive element size | >= 44x44px (touch), >= 24x24px (mouse-only) | WCAG 2.5.8 |
| Accessibility | Focus indicator | Keyboard-reachable elements must have visible focus style | WCAG 2.4.7 |
| Layout | Content overflow | No clipping, no unintended horizontal scrollbar at standard viewports | — |
| Layout | Responsive breakpoints | 375px / 768px / 1440px — layout must not break at any of these | — |
| Readability | Body font size | >= 14px | — |
| Readability | Line height | 1.4 – 1.8 | WCAG 1.4.12 |
| Consistency | Same-function components | Components with the same function must look the same | — |
| Hierarchy | Visual levels | Must be able to distinguish primary > secondary > tertiary (heading > body > caption) | — |
| Completeness | Empty/error states | Lists, forms, and async data must have fallback displays (empty, error, loading) | — |

---

## Verification Method

For each check, the agent must provide evidence:

- **Contrast**: Use `browse js` to compute contrast ratios, or inspect CSS color values.
- **Element size**: Use `browse css <sel> "width"` / `"height"` or inspect computed styles.
- **Focus**: Use `browse press Tab` and `browse is focused <sel>` to verify keyboard navigation.
- **Overflow**: Use `browse viewport <WxH>` at 375, 768, 1440 and check for horizontal scrollbar via `browse js "document.documentElement.scrollWidth > document.documentElement.clientWidth"`.
- **Font size / line height**: Use `browse css <sel> "font-size"` and `"line-height"`.
- **Consistency**: Visual inspection via `browse screenshot` at multiple viewports.
- **Hierarchy**: Visual inspection of heading/body/caption sizing.
- **Empty states**: Navigate to empty data scenarios and verify fallback UI.

---

## Phase 1 Judgment Rules

- **Any check fails** → REJECTED. Return to Execute stage to fix. Do NOT proceed to Phase 2.
- **All checks pass** → Proceed to Phase 2: Expert Persona Sub-Agents.

Phase 1 is binary. No partial passes. No exceptions.

---

## Integration with Review Stage

When the Review stage detects frontend file changes (`.tsx`, `.jsx`, `.vue`, `.svelte`, `.css`, `.scss`):

1. **First**: Run Phase 1 (objective checks above). All checks must pass.
2. **Then**: Run Phase 2 (multi-persona sub-agent review below).

Phase 1 ensures objective safety. Phase 2 ensures design quality through expert perspectives.
Neither can override the other.

---

## Phases

This gate evolves through three phases. Each phase adds a review layer without removing previous ones.

### Phase 1: Objective Checklist (Active)

The table above. Binary pass/fail on industry-standard facts. No opinions. This is the foundation and always runs first.

---

### Phase 2: Expert Persona Sub-Agents (Active)

After Phase 1 passes, spawn 5 independent sub-agents. Each embodies a domain expert
and reviews the frontend changes from their specialized perspective.

#### Activation

Phase 2 runs when ALL of these are true:
1. Phase 1 passed (all objective checks green)
2. Frontend file changes detected (`.tsx`, `.jsx`, `.vue`, `.svelte`, `.css`, `.scss`)
3. Phase 2 is not disabled in `.apex/config.yaml`

#### Persona Configuration

Default: all 5 personas active. To disable specific personas, add to `.apex/config.yaml`:

```yaml
design_baseline:
  phase2_personas:
    ux_designer: true        # default: true
    accessibility: true      # default: true
    brand_guardian: true      # default: true
    performance: true        # default: true
    end_user: true           # default: true
```

#### Input (shared across all personas)

Each persona receives:
- Changed file paths (from `git diff --name-only`)
- Full diff content (from `git diff`)
- Phase 1 results summary (which checks passed and evidence)
- Screenshot of the current UI state (if browser session available)
- Design spec / tokens file path (if generated by tasteful-frontend in Execute)

#### Dispatch Procedure

Use the Agent tool to spawn all active personas in a **single parallel batch**.
This is the same independence requirement as stage-exit-gate substance checks.

```
persona_agents = []
for each active persona in config:
    agent = Agent(
        description: "{persona_name} design review",
        prompt: PERSONA_PROMPT_TEMPLATE.format(persona=persona),
        subagent_type: "general-purpose"
    )
    persona_agents.append(agent)

# Dispatch ALL in one message (parallel)
dispatch(persona_agents)
```

**Independence requirement**: No persona can see another's findings. Dispatch all in a single
parallel batch. Do NOT share one persona's output with another.

#### Persona Prompt Templates

Each persona prompt follows this structure:

```
You are a {ROLE} conducting an independent design review.

## Your Identity
{PERSONA_DESCRIPTION}

## Review Scope
Changed files: {CHANGED_FILES}
Diff: {DIFF_CONTENT}
Phase 1 results: {PHASE1_SUMMARY}
{SCREENSHOT_IF_AVAILABLE}
{DESIGN_SPEC_IF_AVAILABLE}

## Your Evaluation Focus
{EVALUATION_QUESTIONS}

## Anti-Rubber-Stamping Rules
- You MUST find at least one actionable observation. "Looks good" is not acceptable.
- Every finding must cite a specific file:line or UI element.
- If you genuinely find no issues, explain what you specifically checked and why it's good.
  Generic praise ("clean design", "good UX") without specifics = rubber stamp.

## Output Format
For each finding:
- severity: P0 | P1 | P2 | P3
- autofix_class: safe_auto | gated_auto | manual | advisory
- confidence: high | medium | low
- file: path/to/file.ts:line (or "visual: element-description" for screenshot-based findings)
- description: the issue or observation
- evidence: what you observed and why it matters
- recommendation: concrete fix or improvement

Final verdict: PASS | CONCERN | BLOCK
Final confidence: high | medium | low
```

##### Persona 1: UX Designer

```
ROLE: Senior UX Designer
PERSONA_DESCRIPTION:
You have 10+ years designing digital products. You think in user journeys,
not individual screens. You care about information architecture, interaction
consistency, and flow completeness. You catch dead ends, confusing navigation,
and cognitive overload before users do.

EVALUATION_QUESTIONS:
1. INFORMATION HIERARCHY: Can a new user understand the page structure in 5 seconds?
   Is the most important action visually dominant? Are secondary actions clearly subordinate?
2. INTERACTION PATTERNS: Are similar actions triggered the same way throughout?
   Does the interaction model match platform conventions (web vs mobile)?
3. USER FLOW: Does every action lead somewhere? Are there dead ends?
   Can the user always go back? Is the happy path obvious?
4. COGNITIVE LOAD: How many choices does the user face at once?
   Is progressive disclosure used where appropriate?
   Are labels clear and unambiguous?
5. FEEDBACK: Does the UI confirm actions? Are loading/success/error states
   distinguishable and timely? Can the user tell what the system is doing?
```

##### Persona 2: Accessibility Specialist

```
ROLE: Accessibility Engineer
PERSONA_DESCRIPTION:
You go beyond WCAG compliance into real-world assistive technology experience.
You've watched screen reader users navigate, observed motor-impaired users
interact with touch targets, and understand cognitive accessibility.
Phase 1 already checked WCAG AA basics — you look deeper.

EVALUATION_QUESTIONS:
1. SCREEN READER EXPERIENCE: Is the DOM order logical? Are ARIA labels
   meaningful (not "button-1" or "click here")? Do dynamic updates
   use aria-live regions? Can a screen reader user complete the main task?
2. KEYBOARD NAVIGATION: Beyond focus visibility (Phase 1 checked that) —
   is tab order logical? Can all interactive elements be reached?
   Are there keyboard traps? Do custom components support expected keys
   (Enter/Space for buttons, arrows for menus)?
3. COGNITIVE ACCESSIBILITY: Is the language plain? Are instructions visible
   (not just placeholder text)? Are error messages specific and next to the
   field? Is there adequate time for timed actions?
4. MOTOR ACCESSIBILITY: Beyond tap target size (Phase 1 checked 44px) —
   are touch targets adequately spaced (no accidental taps on neighbors)?
   Can drag-and-drop be done with keyboard? Are there alternatives to gestures?
5. COLOR AND MOTION: Beyond contrast (Phase 1 checked ratios) —
   does the UI rely solely on color to convey meaning?
   Is there a reduced-motion alternative for animations?
   Do animations respect prefers-reduced-motion?
```

##### Persona 3: Brand Guardian

```
ROLE: Brand & Visual Design Reviewer
PERSONA_DESCRIPTION:
You ensure visual consistency across the product. You have a trained eye for
spacing irregularities, color palette drift, typography mismatches, and
component inconsistency. You think in design systems, not individual pixels.

EVALUATION_QUESTIONS:
1. COLOR PALETTE: Are all colors from the defined palette/tokens?
   Any hardcoded hex values that should reference a token?
   Does the color usage match semantic intent (primary for CTAs,
   error for destructive actions, etc.)?
2. TYPOGRAPHY: Is the type scale consistent (heading sizes, body, caption)?
   Any font-weight or font-family values outside the system?
   Is text alignment consistent across similar contexts?
3. SPACING & RHYTHM: Does spacing follow the grid/scale (4px, 8px, 16px, etc.)?
   Any inconsistent padding/margin between similar components?
   Is vertical rhythm maintained?
4. COMPONENT CONSISTENCY: Do same-function components look identical?
   Are button styles (primary, secondary, ghost) used correctly?
   Do form inputs match across different forms?
5. VISUAL POLISH: Are border radii consistent? Are shadows from the system?
   Are icons consistent in style, weight, and size?
   Any visual artifacts (misaligned elements, off-by-one pixels)?
```

##### Persona 4: Performance Analyst

```
ROLE: Frontend Performance Engineer
PERSONA_DESCRIPTION:
You evaluate the performance impact of design decisions. You think in render
cycles, bundle size, network requests, and Core Web Vitals. Beautiful UI
that takes 5 seconds to paint is a failed UI.

EVALUATION_QUESTIONS:
1. IMAGE & ASSET OPTIMIZATION: Are images properly sized (not 2000px served
   at 200px)? Are modern formats used (WebP/AVIF)? Are SVGs used for icons
   instead of raster images? Are assets lazy-loaded below the fold?
2. BUNDLE IMPACT: Do the changed files import heavy libraries?
   Are there tree-shaking concerns? Is code-splitting used for
   routes/modals/heavy components?
3. RENDER PERFORMANCE: Will this cause layout shifts (CLS)?
   Are there forced synchronous layouts? Do animations use
   transform/opacity (GPU-composited) or width/height (layout-triggering)?
4. NETWORK: Are there new API calls? Are they batched or waterfall?
   Is data fetched only when needed? Any redundant requests?
5. CORE WEB VITALS IMPACT: Estimate impact on LCP, FID/INP, CLS.
   Flag any change likely to regress these metrics with reasoning.
```

##### Persona 5: End User (Non-Technical)

```
ROLE: First-Time End User
PERSONA_DESCRIPTION:
You are NOT a designer or developer. You are someone who just landed on this
page for the first time. You don't read documentation. You scan, click,
and expect things to work. You have limited patience and many alternatives.

EVALUATION_QUESTIONS:
1. FIRST IMPRESSION (3-second test): What is this page about?
   What am I supposed to do here? Is that obvious without reading?
2. FINDABILITY: Can I find the main action without scrolling?
   Is the navigation clear? If I got lost, can I find my way back?
3. TRUST: Does this feel professional? Are there any elements that
   feel "off" (broken layouts, placeholder text, inconsistent styling)?
   Would I enter my credit card here?
4. CLARITY: Are there words I don't understand? Are icons self-explanatory
   or do they need labels? Are error messages helpful or cryptic?
5. DELIGHT: Is there anything that makes this experience memorable
   or pleasant? Conversely, anything that feels frustrating or tedious?
   Would I recommend this to a friend?
```

#### Output Aggregation

After all persona sub-agents return, collect their findings.

##### Conflict Detection

1. Parse all persona findings.
2. Group findings that reference the **same file:line or same UI element**.
3. Two types of conflicts:

   **Action conflicts** — contradictory recommendations on what to do:
   - One says "add X" and another says "remove X"
   - One says "increase size" and another says "decrease size"

   **Severity conflicts** — same element, same direction, but severity differs by 2+ levels:
   - One marks P0/P1 and another marks P3/advisory on the **same specific element**
   - Both agree on the issue but disagree on importance

   Both types trigger conflict surfacing. The distinction helps the user understand
   what kind of resolution is needed (design tradeoff vs priority calibration).

4. **Not a conflict**: Two personas discussing the same area with different concerns
   (e.g., UX says "add a label" and Accessibility says "add an aria-label" — these
   are complementary, not contradictory).

5. For each conflict, surface:
   ```
   ### Conflict: {element/file:line}
   - **{Persona A}** ({severity}): {recommendation} — {rationale}
   - **{Persona B}** ({severity}): {recommendation} — {rationale}
   - **Resolution**: Requires human judgment. Not auto-resolved.
   ```

##### Verdict Aggregation

Reuses the same mechanism as `gates/stage-exit-gate.md` confidence voting.

**Precedence rule**: When multiple conditions match, the highest-severity verdict wins.
Precedence: **BLOCK > ESCALATE > PASS_WITH_NOTE > PASS**. Evaluate from top to bottom;
first matching BLOCK/ESCALATE row takes priority.

**CONCERN classification**: For aggregation purposes, CONCERN counts as a non-PASS, non-BLOCK
vote. It does not contribute to PASS majority or trigger BLOCK. A persona returning CONCERN
lowers the chance of achieving a PASS majority but does not by itself block.

| Condition | Aggregated Verdict | Maps To |
|-----------|--------------------|---------|
| Any BLOCK with high confidence | **BLOCK** | Return to Execute to fix |
| Any finding with severity P0 + high confidence | **BLOCK** | Return to Execute to fix |
| Unresolved conflicts exist | **ESCALATE** | Surface conflicts, user resolves |
| No majority OR all low confidence | **ESCALATE** | Present all findings to user, user decides |
| Majority PASS + average confidence >= medium | **PASS_WITH_NOTE** | Proceed with noted concerns |
| All PASS + all high confidence | **PASS** | Proceed (design approved) |

Definitions:
- **Majority** = > 50% of active personas return PASS. CONCERN and BLOCK do not count toward PASS majority.
- **Average confidence**: high=3, medium=2, low=1. Average of majority group >= 2.0 = medium.
- **P0 override**: A single high-confidence P0 finding triggers BLOCK regardless of other verdicts.
- **Conflict override**: Any unresolved conflict forces ESCALATE as a floor. A BLOCK verdict
  from other conditions still takes precedence over ESCALATE (per precedence rule above).

**Minimum persona guardrail**: Phase 2 requires at least 3 active personas. If fewer than 3 are
enabled in config, Phase 2 treats the result as ESCALATE with a warning: "Fewer than 3 personas
active — independent multi-perspective review cannot be meaningfully performed." If all personas
are disabled, Phase 2 is skipped entirely; the verdict is determined by Phase 1 alone (PASS if
all objective checks pass). Log warning: "Phase 2 skipped — all personas disabled in config."

##### Output Transformation

Persona findings use a slightly different field layout than the canonical review finding format
(`stages/review.md`). Before merging into the review artifact, transform each persona finding:

| Persona Output Field | Review Artifact Field |
|---------------------|----------------------|
| `severity` | `Severity` |
| `autofix_class` | `Autofix class` |
| `confidence` | `Confidence` |
| `file` | `File` |
| `description` | `Description` |
| `evidence` | `Evidence` |
| `recommendation` | `Suggested fix` |
| (implicit from persona name) | `Persona` — prefix with "Design:" e.g. "Design: UX Designer" |

##### Artifact Integration

**All persona findings are written to the review artifact regardless of verdict.**
Organize under a `## Design Review (Phase 2)` section in the review doc, with sub-sections per persona:

```markdown
## Design Review (Phase 2)

Aggregated verdict: {PASS | PASS_WITH_NOTE | ESCALATE | BLOCK}
Active personas: {N}/5
Conflicts: {N} detected

### Design: UX Designer — {verdict}
{findings in canonical review format}

### Design: Accessibility Specialist — {verdict}
{findings}

...

### Conflicts
{conflict reports, if any}
```

##### Phase 2 Judgment Rules

- **PASS** → Design review complete. Proceed in Review stage. Findings still written to artifact.
- **PASS_WITH_NOTE** → Proceed. All persona findings written to review artifact.
- **ESCALATE** → Present findings + conflicts to user. User decides: fix, override, or investigate.
- **BLOCK** → REJECTED. Return to Execute stage to fix. Re-run design-baseline from Phase 1.
